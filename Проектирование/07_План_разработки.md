# План разработки системы управления менторами

## 1. Общий подход к разработке

### 1.1. Методология

**Итеративная разработка** - поэтапное создание функционала с постоянным тестированием

**Принципы**:
- Сначала базовый функционал, затем улучшения
- После каждого этапа - рабочая версия системы
- Тестирование после каждой фичи
- Возможность использовать систему на ранних этапах

### 1.2. Приоритизация функций

**Must Have** (Обязательно):
- CRUD операции для менторов
- Добавление записей о работе
- Генерация актов выполненных работ
- Просмотр списка менторов со статистикой

**Should Have** (Желательно):
- Фильтры и поиск
- Экспорт данных
- Архив актов
- Детальная статистика

**Could Have** (Можно добавить):
- Графики и визуализация
- Импорт данных
- Продвинутые настройки
- Темная тема

**Won't Have** (Не в первой версии):
- Авторизация
- Многопользовательский режим
- Backend
- Email уведомления

## 2. Этапы разработки

### Этап 0: Подготовка (1-2 дня)

**Цель**: Подготовить окружение и базовую структуру проекта

**Задачи**:
1. Создать структуру папок проекта
2. Настроить редактор кода (VS Code + расширения)
3. Инициализировать Git репозиторий
4. Создать базовый HTML шаблон
5. Подключить шрифты и иконки
6. Создать базовые CSS файлы (сброс стилей, переменные)
7. Настроить систему сборки (если требуется)

**Результат**: Готовая структура проекта, базовые файлы

**Проверка**: Открывается пустая главная страница с правильными стилями

**Задачи**:

2. Реализовать StorageService для работы с LocalStorage
3. Реализовать функции CRUD для менторов
4. Добавить валидацию данных
5. Создать генератор ID
6. Тестирование сохранения/загрузки данных

**День 3-4: UI компоненты**
1. Создать базовые стили (цвета, типографика, spacing)
2. Реализовать компонент Button
3. Реализовать компонент Input
4. Реализовать компонент Modal
5. Реализовать компонент Toast (уведомления)
6. Создать общий layout (header, container, footer)

**Результат**: 
- Работающая система хранения данных
- Базовые переиспользуемые UI компоненты
- Общий layout системы

**Проверка**:
- Можно сохранить и загрузить ментора через консоль

### Этап 2: CRUD операции для менторов (4-5 дней)

**Цель**: Полноценная работа с менторами - создание, просмотр, редактирование, удаление

**Задачи**:

**День 1-2: Список менторов (index.html)**
1. Создать главную страницу
2. Реализовать загрузку менторов из LocalStorage
3. Создать таблицу со списком менторов
4. Добавить базовую статистику (карточки с числами)
5. Реализовать навигацию к другим страницам
6. Добавить empty state (когда нет менторов)

**День 3: Создание ментора (create-mentor.html)**
1. Создать страницу с формой
2. Реализовать все поля формы
3. Добавить валидацию на клиенте
4. Реализовать сохранение ментора
5. Добавить уведомления об успехе/ошибке
6. Реализовать перенаправление после создания

**День 4: Просмотр ментора (view-mentor.html)**
1. Создать страницу профиля ментора
2. Загрузка данных по ID из URL
3. Отображение всей информации о менторе
4. Добавить базовую статистику (пока без реальных данных)
5. Кнопки навигации к редактированию и удалению

**День 5: Редактирование и удаление**
1. Создать страницу edit-mentor.html
2. Загрузка и предзаполнение формы
3. Реализовать обновление данных
4. Реализовать функцию удаления с подтверждением
5. Обработка edge cases (ментор не найден и т.д.)

**Результат**:
- Полностью рабочий CRUD для менторов
- Можно создавать, просматривать, редактировать и удалять менторов
- Все данные сохраняются в LocalStorage

**Проверка**:
- Сценарий: создать 3 менторов, просмотреть, отредактировать одного, удалить другого
- После перезагрузки страницы данные сохранены

### Этап 3: Записи о работе (4-5 дней)

**Цель**: Возможность добавлять и управлять записями о выполненной работе

**Задачи**:

**День 3: Просмотр записей (view-works.html)**
1. Создать страницу со списком всех работ
2. Таблица с записями

4. Кнопки редактирования и удаления записи

**День 4-5: Фильтры и функциональность**
1. Добавить фильтры (по ментору, по периоду)

3. Добавить пагинацию
4. Реализовать редактирование записи

6. Обновление статистики менторов после изменений

**Результат**:
- Можно добавлять записи о работе для менторов
- Просмотр всех записей в виде таблицы

**Проверка**:
- Добавить 10-15 записей для разных менторов
- Отфильтровать по одному ментору
- Проверить, что суммы правильно рассчитываются

### Этап 4: Генерация актов (5-6 дней)

**Цель**: Формирование и генерация PDF актов выполненных работ

**Задачи**:

**День 1: Настройки системы (settings.html)**
1. Создать страницу настроек
2. Форма для ввода данных заказчика
3. Сохранение настроек в LocalStorage
4. Валидация обязательных полей

**День 2-3: Формирование акта (generate-report.html)**
1. Создать страницу генерации акта
2. Шаг 1: Выбор ментора и периода
3. Загрузка записей о работе за период
4. Шаг 2: Отображение записей с чекбоксами
5. Расчет итогов (часы, сумма)
6. Генерация номера акта

**День 4: Функция суммы прописью**
1. Реализовать конвертацию числа в текст
2. Правильное склонение (рубль/рубля/рублей)
3. Тестирование на разных числах

**День 5-6: PDF генерация**
1. Подключить библиотеку jsPDF или pdfmake
2. Настроить шрифт с поддержкой кириллицы
3. Создать шаблон акта
4. Реализовать заполнение данными
5. Создание таблицы работ
6. Сохранение и скачивание PDF
7. Сохранение акта в архив

**Результат**:
- Настройки заказчика заполнены
- Можно сформировать акт за период
- Генерируется красивый PDF документ
- Акт сохраняется в систему

**Проверка**:
- Заполнить настройки заказчика
- Создать акт для ментора за месяц
- Проверить PDF: все данные корректны, таблица форматирована, сумма прописью правильная

## 4. Зависимости между задачами

### Критический путь

```
Подготовка → Инфраструктура → CRUD менторов → Записи о работе → Генерация актов
```

Эти этапы должны выполняться последовательно, так как каждый зависит от предыдущего.

### Параллельные работы

После этапа 2 (CRUD менторов) можно параллельно:
- Работать над дизайном страниц этапа 3
- Готовить документацию
- Создавать тестовые данные

После этапа 5 можно параллельно:
- Добавлять графики (этап 7)
- Работать над экспортом (этап 6)
- Начинать тестирование готовых частей (этап 8)

## 5. Риски и митигация

### Потенциальные риски

**Риск 1: Переполнение LocalStorage**
- Вероятность: Средняя
- Влияние: Высокое
- Митигация: 
  - Добавить проверку размера данных
  - Предупреждать пользователя заранее
  - Функция экспорта и архивирования старых данных

**Риск 2: Проблемы с генерацией PDF**
- Вероятность: Средняя
- Влияние: Высокое
- Митигация:
  - Выбрать проверенную библиотеку (jsPDF, pdfmake)
  - Протестировать на ранних этапах
  - Иметь запасной вариант (экспорт в HTML для печати)

**Риск 3: Сложность с кириллицей в PDF**
- Вероятность: Высокая
- Влияние: Среднее
- Митигация:
  - Использовать библиотеку с поддержкой Unicode
  - Встроить кириллический шрифт
  - Тестировать рано и часто

**Риск 4: Несовместимость с браузерами**
- Вероятность: Низкая
- Влияние: Среднее
- Митигация:
  - Использовать стандартные Web API
  - Проверять совместимость на caniuse.com
  - Тестировать в разных браузерах регулярно

**Риск 5: Потеря данных пользователем**
- Вероятность: Средняя
- Влияние: Критическое
- Митигация:
  - Функция экспорта резервных копий
  - Напоминания делать бэкапы
  - Автоматическое сохранение

**Риск 6: Недооценка времени разработки**
- Вероятность: Высокая

## 7. Критерии качества

### Definition of Done (Определение готовности)

Функция считается готовой, если:
1. Код написан и работает согласно требованиям
2. Проведено ручное тестирование
3. Нет критичных багов
4. UI соответствует дизайну
5. Код прокомментирован (для сложных частей)
6. Данные корректно сохраняются и загружаются
7. Функция протестирована в разных браузерах
8. Добавлена обработка ошибок

## 9. Ежедневная рутина разработки

### Рекомендуемый workflow

**Начало дня**:
1. Просмотр плана на день
2. Pull последних изменений (если работа в команде)
3. Выбор приоритетной задачи

**В процессе работы**:
1. Разработка функции
2. Ручное тестирование
3. Коммит изменений с понятным сообщением
4. Переход к следующей задаче

**Конец дня**:
1. Push изменений в репозиторий
2. Обновление статуса задач
3. Планирование на следующий день
4. Запись найденных проблем/идей

### Частота коммитов

- Коммитить после завершения логической единицы работы
- Минимум 2-3 коммита в день
- Понятные сообщения коммитов на русском или английском

Примеры:
- "Добавлена форма создания ментора"
- "Реализована валидация email"
- "Исправлен баг с сохранением даты"
